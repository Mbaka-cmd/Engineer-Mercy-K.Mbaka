School Management SaaS for Chuka Girls

A multi-tenant platform that moves a school's back office (records, fees, attendance, exams, library, timetables and reports) onto one secure system with four role-based portals.

  • Django
  • PostgreSQL
  • REST APIs
  • JWT + RBAC
  • M-Pesa Daraja
  • WeasyPrint
  • Docker
  • Render

01Project overview

The platform replaces paper registers, fee receipts and hand-compiled report cards with one web system. One codebase serves many schools; each school's data is isolated. Chuka Girls Secondary School is a tailored deployment of it.

02Problem and requirements

School administration involves many people with different needs working on the same records: administrators, teachers, students and parents. The system had to:

  • keep student, fee, attendance, exam and library records in one consistent place;
  • let parents pay fees from their phones with M-Pesa and have payments recorded reliably;
  • show each person only what their role allows;
  • produce documents such as invoices and report cards without manual work;
  • serve more than one school without mixing their data.

03My role and contribution

I designed and built the system end to end: data model, backend modules, API layer, authentication and access control, the M-Pesa integration, document generation, and deployment configuration.

04System architecture

Four role-based portals call a Django application and REST API. Business modules sit behind that layer, backed by PostgreSQL. External services are called from the backend, never from the browser.

05Database design

PostgreSQL holds a relational model around schools, users and roles, students and guardians, classes, fee structures, invoices and payments, attendance, exams and results, library records and timetables. Foreign keys and constraints carry the integrity rules, so the database refuses inconsistent data even if application code has a bug.

Trade-off: a shared database with a school identifier on tenant data is simple to run and migrate for a small team. The cost is that tenant isolation depends on every query being scoped correctly, which is why scoping is enforced in one layer rather than repeated in each view.

06Backend modules

The code is organised by domain: fees and payments, attendance, examinations and report cards, library management, timetables, and reporting. Each module owns its models and business rules, which keeps changes in one area from leaking into the others.

07API design

The portals use REST endpoints with validation on input, consistent status codes and error responses, and permission checks on every route.

08Authentication and authorization

Users sign in with JWT-based authentication. Role-based access control then decides what each role can see and do: a parent sees only their own child's records, and a teacher cannot reach admin-only financial data. Authentication answers "who are you"; authorization answers "what may you do here", and they are checked separately on every request.

09Payment integration

A parent receives an M-Pesa STK Push prompt on their phone and pays a fee. The initial API response only means the prompt was sent, not that money moved, so a payment is treated as a state that moves from initiated to pending to success or failure, confirmed by Safaricom's callback.

Callbacks can arrive more than once. The backend identifies each payment by its Checkout Request ID and, if a record already exists, acknowledges the callback without processing it again. I wrote about this in the idempotency article.

10Challenges and technical decisions

  • Duplicate callbacks: solved by treating the Checkout Request ID as the idempotency key.
  • Tenant isolation: centralised scoping so a missed filter in one view cannot expose another school's data.
  • Role complexity: four portals share one API, with permissions defined per role rather than per screen.
  • Documents: invoices and report cards are rendered as PDFs on the server with WeasyPrint, so output is consistent regardless of the user's device.

11Deployment

The application is containerised with Docker and served by Gunicorn behind Nginx, deployed on Render, with configuration supplied through environment variables rather than committed to the code.

13Results and lessons learned

The system is live and covers the school's administrative workflows from one place. The biggest lessons were to design for repeated and failed requests from the start, to enforce isolation and permissions centrally, and to model money as a state machine. Next on my roadmap for this project: automated tests for the payment flow and a CI pipeline.
