School Management SaaS

A multi-tenant platform for student administration, fees and M-Pesa workflows, attendance, examinations, library management, timetables and reports, with four role-based portals.

01Overview

Schools run on records that many people touch: student details, fees, attendance, exam results, library stock, timetables. This platform puts them in one system with separate portals for each kind of user, and supports more than one school on the same platform.

02Problem and objectives

The system had to:

  • keep student, fee, attendance, examination and library records consistent in one place;
  • let fees be paid by M-Pesa and recorded reliably;
  • show each person only what their role allows;
  • produce reports and documents without manual compilation;
  • keep one school's data separate from another's.

03My role

I designed and built the backend: data model, modules, API layer, authentication and access control, and the M-Pesa integration, and handled the application's deployment configuration.

04Architecture and stack

Role-based portals talk to a Django application and REST API. Business modules sit behind it, backed by PostgreSQL. M-Pesa Daraja is called from the backend, never from the browser. The system is deployed on Render.

05Database and tenancy

PostgreSQL holds relational data for schools, users, students, fees and payments, attendance, examinations, library records and timetables. Foreign keys and constraints carry the integrity rules, so the database rejects inconsistent data even when application code has a bug.

Why this matters for multi-tenancy: every query has to be limited to the requesting user's school. Doing that in one consistent place is safer than repeating a filter in every view, because a single missed filter would expose another school's records.

06Roles and permissions

Four portals serve four kinds of user. Role-based access control decides what each role may view and change: a parent should only reach their own child's information, and administrative or financial screens are restricted to staff with the right role.

07API design and authentication

The portals use REST endpoints secured with JWT authentication. Authentication (who you are) and authorization (what you may do) are checked as separate steps on every request, with validation on incoming data and consistent error responses.

08Payment integration

Fees are paid through M-Pesa Daraja. The backend starts an STK Push, the payer approves on their phone, and Safaricom later sends a callback with the result. The first API response only means the prompt was sent, so a payment is treated as a state that moves from initiated to pending to success or failure, and is verified rather than assumed.

Callbacks can be delivered more than once. My approach, described in the idempotency article, is to identify each transaction by its Checkout Request ID and acknowledge a repeat callback without processing it again.

09Errors, consistency and security

  • Validate input at the API boundary.
  • Use database constraints and transactions for consistency.
  • Keep secrets and configuration out of the code.
  • Call external services only from the backend.
  • Return clear errors without exposing internals.

10Reports and deployment

The platform produces reports for the school's records. The application is deployed on Render, with configuration provided through the environment.

11Challenges and decisions

  • Repeated callbacks: make payment processing safe to repeat.
  • Keeping schools separate: scope data centrally instead of per view.
  • Many roles, one API: define permissions per role rather than per screen.
  • Trade-off: one platform for many schools is cheaper to run and update, but isolation then depends on careful scoping and good tests.
