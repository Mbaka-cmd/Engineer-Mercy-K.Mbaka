Why Every Backend Developer Should Understand Idempotency Before Building Payment Systems

Mercy Mbaka · June 2026 · 4 min read

One of the biggest lessons I learned while integrating M-Pesa wasn't about APIs - it was about a distributed systems concept called idempotency. Once I understood it, it changed how I designed every backend system.

The Theory

In distributed systems, a request can be delivered more than once.

Not because the client wants it to.

Because networks fail.

Imagine you're buying coffee using your mobile banking app. You tap Pay. The money leaves your account. At the exact same moment, your internet connection drops. Your phone never receives confirmation.

What do you do? You press Pay again.

Did you intend to pay twice? No. But from the server's perspective, it has now received two payment requests.

This is one of the oldest problems in distributed computing. The solution is idempotency.

An idempotent operation produces the same final result whether it is executed once or multiple times.

Why This Matters in Real Life

Think about an ATM. Suppose you request KSh 5,000. The ATM dispenses the cash, but before it prints the receipt, the screen freezes.

You don't know whether the transaction completed. If you press the button again and the ATM dispenses another KSh 5,000, the bank has a serious problem.

Instead, banking systems assign every transaction a unique identifier. If the same request arrives again, the system recognizes it and returns the original result instead of processing it a second time.

This principle is used by banks, airlines, hospitals, e-commerce platforms, and payment gateways because duplicate operations can have real financial consequences.

Where I Encountered It

While building backend systems with Django and integrating the M-Pesa Daraja API, I learned that receiving a successful callback doesn't always mean you'll receive it only once.

If Safaricom doesn't receive an HTTP 200 response quickly enough, it may retry the callback. Without additional safeguards, the application could:

  • activate the same subscription twice,
  • insert duplicate payment records,
  • send multiple confirmation messages,
  • or update account balances incorrectly.

At first glance, this looks like a bug in the API. It isn't. It's expected behavior in distributed systems. The responsibility lies with the backend application to process repeated requests safely.

How I Applied the Concept

Instead of immediately processing every callback, I first identify the transaction using a unique reference such as the Checkout Request ID.

If a transaction with the same identifier already exists in the database, the request is acknowledged but ignored.

Conceptually, the workflow becomes:

Webhook arrives
        |
        v
Does transaction already exist?
        |
   +----+----+
   |         |
  No        Yes
   |         |
Process   Return HTTP 200
Payment   Without Reprocessing

This guarantees that one payment creates one transaction, regardless of how many times the callback is delivered.

How This Improved My Engineering Skills

Learning idempotency changed more than my payment integration. It changed how I think about backend architecture.

Before, I focused on making requests succeed. Now, I design systems that behave correctly even when requests are repeated, delayed, or interrupted.

Whenever I build an API, I ask questions such as:

  • What happens if the client retries this request?
  • What happens if the server crashes halfway through processing?
  • Can this operation be executed twice without corrupting data?
  • How can the database enforce consistency?

These questions have made my applications more reliable and easier to maintain.

Beyond M-Pesa

Once I understood idempotency, I began seeing the same pattern everywhere.

When creating user accounts, duplicate registration requests should not create duplicate users. When processing inventory, the same order should not reduce stock twice. When generating invoices, refreshing a browser should not issue multiple invoices.

Although the business logic changes, the engineering principle remains the same: design operations that remain correct even when the unexpected happens.

Final Thoughts

One API integration introduced me to a concept that appears across nearly every production system.

Idempotency isn't just a payment feature. It's a fundamental principle of distributed systems.

Understanding it has made me a more thoughtful backend engineer, encouraging me to design software that prioritizes correctness, resilience, and predictable behavior over simply making the happy path work.

That lesson has influenced every Django application I have built since.
